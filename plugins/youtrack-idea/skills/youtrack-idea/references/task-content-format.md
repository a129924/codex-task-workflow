# Task 內容規則

Task 保存一件事的目前概要與重要變更，讓本人或新的 Agent Session 不依賴原對話，也能知道為何做、目前方向、所在階段、下一步及阻礙。同一件事從發想到結案沿用同一個識別；改名、改方向或切換階段都不另建替代識別。

使用 [Markdown 模板](task-content-format.template.md) 建立或更新紀錄；[情境示例](task-content-format.examples.md) 示範手寫及 Agent 整理。本文規範內容，不指定 YouTrack 實體欄位、系統映射或整合操作，也不代表產品能力已驗證。

## 名稱與共用格式

名稱採單行 `<工作對象>：<目的或期望結果>`，依已知目的命名，不把尚未確認的方案寫成既定結果。更名時識別維持不變。

本人手寫與 Agent 整理使用相同區段、欄位及順序：

```markdown
# <工作對象>：<目的或期望結果>

- Task 識別：<值>
- 專案：<值>
- 標籤：<值>

## 目的與背景
- 目的：<值>
- 已知背景：<值>

## 目前方向
- 方向：<值>
- 主要理由：<值>
- 待釐清：<值>

## 工作狀態
- 階段：<值>
- 下一步：<值>
- 阻礙：<值>

## 參考資料
- <值>

## 重要變更
- <值>

## 結案
- 結案類型：<值>
- 結果或停止原因：<值>
```

`<值>` 是待替換的占位文字，不是有效答案；不得留下空白作為答案。名稱、識別、專案、標籤與階段若由既有系統 metadata 表達，語意仍須一致；如何映射留給整合設計。可複製模板與示例呈現完整結構，便於獨立閱讀。

## 未知、沒有與不適用

| 表達 | 何時使用 | 範例 |
| --- | --- | --- |
| `待釐清：<缺少或尚未決定的內容>` | 未知、未確認、尚未決定 | `待釐清：尚未確認有無阻礙` |
| `無` | 已確認目前沒有 | 已確認沒有參考資料時填 `無` |
| `不適用：<原因>` | 在目前情境不適用 | `不適用：尚未結案` |

不能用「無」代替不知道，也不能用「不適用」跳過未確認的問題。專案、標籤、理由與下一步等欄位都遵守這個區別。建立前尚未取得識別時填 `待釐清：尚未取得識別`；取得後更新 snapshot。沒有方向時，方向填具體待釐清項，主要理由可填 `不適用：尚未形成方向`。尚未結案的兩個結案欄位均填 `不適用：尚未結案`。

已知目的就能留存有效 Idea，方向與下一步可以未知，不要求補滿所有內容。若目的本身尚不清楚，先釐清希望解決的問題，不從技術名詞或零碎對話猜出有效目的。來源互相矛盾時保留矛盾與待確認處，不把較新的文字默認成決策。

## 建立與整理

本人手寫時，先寫已知目的與背景，再填目前方向、階段、下一步和阻礙；其餘未知欄位用明確語意標記。讀完應能理解工作概要，不需要找回原對話。

Agent 整理時，只使用可得來源，將摘要寫進相同欄位，區分已知事實、尚未形成的決策與缺少的資料。來源不足就寫待釐清，不自行補造目的、方案、理由、進展或行動。引用來源時說清楚位置、用途與存取狀態；使用者轉述的內容不能寫成 Agent 已讀原件。

建立、查詢、更新與結案都不依賴 `plan.md`、`step.md`、PR、特定目錄或其他 Skill。Task 不接管參考資料的產生、維護或同步；紀錄按需要主動更新，不承諾背景同步或每個 Session 自動更新。

## 更新 snapshot 與重要變更

名稱、metadata、目的與背景、目前方向、工作狀態、參考及結案呈現「現在」的 snapshot；有新事實時直接修正對應欄位。已確認不存在的事項才改成「無」。

重要目的或方向調整，以及影響恢復理解的階段退回／跳轉，另在重要變更追加：

```text
<先後序號>｜<變更前> → <變更後>｜理由：<已確認理由或待釐清標記>
```

依發生先後使用序號，保留原有順序與理由，不用新的 snapshot 覆寫歷史。已知日期可附記，沒有日期就不補造；理由未知可寫 `理由：待釐清：尚未確認調整原因`。同一次變更可在前後內容同時交代方向及階段。一般措辭修正不要求記錄，不保存全部對話或每個技術步驟。

## 階段的最小內容

所有階段均保留共用結構與 metadata；下表描述應保存的內容，不是系統轉換 gate。依實際工作情況標示階段，可跳過階段或退回，不以欄位是否全知、文件是否存在或 Skill 是否執行判定允許轉換。

| 階段 | Snapshot 最小內容 |
| --- | --- |
| Idea | 已知目的、可得背景、待釐清事項，以及下一步或其待釐清標記；方向可尚未形成 |
| Draft plan | 正在整理的初步方向、可得理由與尚未確定事項 |
| Implementation plan／實作 | 目前實作方向、已知進展、下一步及阻礙；不複製詳細步驟 |
| PR | 目前交付／審查情況、下一步及阻礙；PR 參考可選 |
| Close | 結案類型與實際結果或原因，保留既有方向、重要變更及參考 |

進展可寫在已知背景或方向中；不新增另一套欄位。PR 建立或合併不自動等同完成或 Close。實際狀態名稱與系統映射由後續整合設計處理。

## 參考資料

參考可有零、一或多份，不限制檔名或種類。每筆使用 `位置：…｜用途：…｜存取狀態：…`，可追加缺少資料的說明；存取狀態寫已讀、可存取但尚未讀取、不可存取，或 `待釐清：尚未確認能否存取`，均須符合實際已知情況。沒有參考且已確認時填「無」。

無法存取時保留位置與用途，說明缺少哪些資訊；不可假裝已讀。Task 的目的、方向、階段與下一步仍須留在本文，不以「詳見參考」代替概要。深層設計或測試細節可留在原資料，不必複製全文。

## 結案與回查

結案類型使用「完成」、「取消」或「停止」，階段改為 Close，結果或停止原因保存實際結果或取消／停止原因。「完成」需有已知完成結果；「取消」說明不再需要這件事的原因；「停止」說明決定不再繼續的原因。由 Idea 直接結案也適用，不要求先產生計畫、PR 或執行 Skill。

已結案的下一步可填 `不適用：此 Task 已結案`。仍有未解決問題就保留在待釐清或阻礙中，不因結案改寫成已解決。保留同一識別、最後方向、參考與重要變更，使日後仍可查詢選擇與結果；PR 情況與 Task 結案分別記錄。
