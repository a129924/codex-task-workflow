# Task Workflow 需求 Baseline

本文件提供給 Codex，作為討論與修訂 draft-plan 的需求基準。先確認要解決的問題、工作邊界與預期行為，再決定實作方式。既有 draft-plan 若把特定文件或其他 Skill 當成必要依賴，應依本文件修正。

**核心需求：建立可長期留存、供本人與 Agent 查詢的 Task 紀錄。隔一段時間回來，仍能快速知道一件事為什麼做、目前選擇什麼方向、做到哪裡，以及接下來做什麼。**

**獨立性要求：Task 工作流不依賴 `plan.md`、`step.md`、特定檔名、目錄結構或其他規劃與實作 Skill。文件、設計圖、討論連結與 GitHub PR 都是可選的參考依據，不構成必須一起使用的套餐。**

## 1. 使用背景與目的

使用者是獨立開發者，經常透過 Codex 討論發想，並同時處理多個專案與 Session。工作脈絡分散在對話、文件與 PR；經過週末或連假，容易忘記每件事的目的、進度與當時的選擇。

這套工作流要提供固定的 Task 入口，讓已經討論過的想法有地方留存，降低分心、遺忘、重複討論，以及重新恢復上下文的成本。

日常操作以本人或 Agent 主動建立、查詢、更新與關閉 Task 為主。第一版不需要主動通知、對外溝通或背景追蹤。

## 2. 要解決的問題

- 發想已經有初步輪廓，卻尚未成熟到能寫 Draft plan，缺少合適的留存位置。
- 同時有多件工作，難以快速看出每件事目前的階段與下一步。
- 看得到技術文件，卻不容易找回當時為什麼選擇某個方向。
- 同一件事的討論、文件與 PR 分散，缺少共同入口。
- 原本的 Agent Session 不在眼前時，需要重新解釋整件事情。
- Task 結束後，仍希望查詢過去的方向、重要理由與結果。

## 3. 核心管理單位

一張 Task 代表一件希望持續追蹤的事情，從初步發想到結束，沿用同一個 Task 識別。

建立門檻是：已經與 Agent 大致討論過，知道想解決什麼，但可以還沒有足夠線索、穩定方案或完整計畫。這時就能以 Idea 狀態開單；不需要為了開單而補出尚未成立的方案。

Task 保存恢復工作所需的大方向與摘要。尚未確認的內容應保持待釐清，不應由 Agent 自行補成已定案的決策。

## 4. 必須維持的獨立性

- 沒有任何規劃文件時，仍能建立、查詢、更新與關閉 Task。
- 不要求安裝或執行其他 Draft plan、實作、Review 或 step-tracker Skill。
- 不透過特定檔案是否存在，判定 Task 是否允許建立或切換階段。
- 不要求文件一定放在某個 Repo、資料夾，或使用特定格式。
- 一張 Task 可以有零份、一份或多份參考資料。
- 附加參考資料不代表由此 plug-in 負責產生、維護或同步該資料。

例如，進入 Draft plan 階段表示工作正在整理初步方案；不代表必須存在名為 `plan.md` 的檔案。進入 PR 階段時可以附上 GitHub PR，但並非每件 Task 都需要程式碼變更或 PR。

功能獨立性與原始碼放在哪個 Repo 是不同的決定。無論放在現有 Skill Repo 或另開 Repo，都必須滿足上述要求；本 baseline 不把其中一種 Repo 安排列為必要條件。

## 5. Task 要保存的內容

| 內容 | 要回答的問題 |
| --- | --- |
| 名稱與目的 | 這件事是什麼？希望解決什麼問題？ |
| 所屬專案與標籤 | 它屬於哪個專案？之後怎麼分類與查詢？ |
| 目前方向與主要理由 | 現在傾向怎麼處理？為什麼？有哪些尚未確認的地方？ |
| 目前階段 | 還在發想、規劃、實作、PR，還是已結束？ |
| 下一步與阻礙 | 回來之後先做什麼？目前卡在哪裡？ |
| 可選的參考資料 | 若需要深入理解，可以去哪裡看？ |
| 重要方向變更與結案結果 | 曾經怎麼調整？最後完成、取消或停止的原因是什麼？ |

內容隨工作成熟逐步補充，不要求開單時全部填完。Idea 階段可以只有目的、已知背景、待釐清問題與下一步。

重要方向變更要保留足以理解先後與理由的簡短紀錄，避免更新目前方向後，完全失去先前選擇的脈絡。這不要求保存所有對話或每個技術步驟。

## 6. 參考資料的定位

參考資料可包含本地或 Repo 內的文件、設計圖、外部文件、討論連結與 GitHub PR。`plan.md`、`step.md` 只是可能使用的文件名稱，不是 Task 的固定組件。

Task 應保存參考位置，以及理解其用途所需的簡短說明。詳細設計、實作步驟、測試證據等內容，由原本的文件與工作流程維護，不需要完整複製到 Task。

即使某個參考資料暫時無法存取，Task 內的目的、方向、狀態與下一步仍應可讀；Agent 應說明缺少哪些資料，不應假裝已經讀取。

## 7. 預期生命週期

主要工作路徑為：

**Idea → Draft plan → Implementation plan／實作 → PR → Close**

- 開單是建立紀錄的動作，Idea 是可正式留存的階段。
- 階段描述工作進展，不要求搭配特定文件或執行特定 Skill。
- 不強制每張 Task 走完所有階段；可以依實際情況返回前一階段，或在決定不繼續時結案。
- Close 要留下結果或原因，且關閉後仍能查詢內容、重要方向變更與已附加的參考資料。
- 有 PR 時可關聯到同一張 Task；PR 建立或合併不自動等同 Task 完成。

實際狀態名稱與結案條件由 draft-plan 對應到採用的系統及專案規則，但不得把特定規劃文件列為這個 plug-in 的通用必要依賴。

## 8. 第一版提供的能力與限制

第一版透過 Agent 支援四類操作：

1. 建立 Task：將已討論的發想整理為可留存的高層摘要。
2. 查詢 Task：依專案、標籤與狀態尋找工作，讀取單張 Task，並能包含已關閉項目。
3. 更新 Task：記錄方向、階段、下一步、阻礙與參考資料；必要時補上重要變更理由。
4. 關閉 Task：保存結果或停止原因，保留日後查詢能力。

第一版由使用者在需要時請 Agent 操作。能夠留存的內容以實際寫入 Task 的資訊為準，不承諾每個 Session 自動記得更新。

使用條件為：

- Task 紀錄可保持私人存取，不必與 public code repo 的外部 Issue 混在一起。
- 支援跨專案收集，同時能按專案與標籤清楚篩選。
- 以本人加至多一個 bot 的規模評估免費方案，避免持續累積 Task 造成張數額度焦慮。
- 整合優先採官方支援，或社群廣泛採用的工具；沒有合適選項時，再評估自行補足。
- 已討論的方案方向是 Codex plug-in 搭配 YouTrack；具體介面、Skill 結構、驗證與設定方式由 draft-plan 處理。

## 9. 第一版範圍外

- 強制 Agent 更新狀態的 Hook、阻擋機制或背景同步。
- Ghostty 視窗辨識、Session 命名、Session 恢復與多 Agent 協調。
- 執行或接管既有的規劃、實作、Review 與 step-tracker 工作流。
- 自動掃描所有 Repo、匯入歷史文件，或同步文件全文。
- 自動追蹤 GitHub PR 事件、建立 PR 或自動結案。
- 自建任務管理平台、專屬 Dashboard 或完整對話記憶系統。

## 10. 驗收情境

1. **沒有文件也能使用**：只有已討論的發想，沒有 `plan.md`、`step.md`、PR 或其他工作流 Skill，仍可建立 Idea Task，之後查詢、更新並在決定停止時留下原因結案。
2. **可選附加參考**：同一張 Task 後續可以附加任意名稱的文件或 PR，不需要先調整原本的檔案結構，也不因此接管文件維護。
3. **連假後恢復工作**：從某個專案的 Task 清單找到未完成工作，讀取目的、方向、階段與下一步，就能和 Agent 繼續討論；必要時再查看參考資料。
4. **換 Session 仍能理解**：新的 Agent Session 不依賴原始對話，能透過 Task 紀錄理解工作概要，並知道哪些內容仍待釐清。
5. **結案後可回查**：Task 關閉後，仍能查詢當時的重要選擇、變更原因、最終結果，以及已附加的文件或 PR。

後續 draft-plan 的設計與取捨，應以這些情境是否成立作為檢查依據。
