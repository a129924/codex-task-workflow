# Task Workflow 行為契約

本契約定義使用者如何觸發 Task 操作、Agent 如何整理與回報，以及同一張 Task 如何更新與轉換階段。它沿用 [需求 baseline](task-workflow.baseline.md) 與 [Task 內容規則](task-content-format.md)，不改動共用格式、系統欄位或既有資料。本文是行為定義，不代表 plugin 或 YouTrack 整合已能執行。

- Mission：BC Mission；Primary BC 暫稱「Task 工作脈絡管理」。
- **Goal**：只讀同一張 Task，就能知道目的、方向、現況與下一步，或清楚知道缺少什麼。
- **Non-Goal**：不代替規劃、實作、Review 或 PR 管理；不實作 plugin、同步服務或自動推進。
- **In-Scope**：建立、讀取、更新、切換階段、結案；跳階、返回、提早停止；snapshot、重要變更，以及缺口、矛盾、參考失效的處理。
- **Out-Of-Scope**：plugin folder／manifest／runtime、認證與 YouTrack 欄位映射、強制文件／Skill／step-tracker、背景操作、跨專案搜尋介面、遷移及已結案 Task 重開。

[桌面情境與驗收](testcases/TC-TASK-WORKFLOW-CONTRACT-001.md) 提供可重演紀錄；[生命週期圖](diagrams/task-workflow-contract/lifecycle.html) 僅呈現典型路徑及跳轉示例，不是完整轉換白名單。圖中文字為繁體中文，固定 Viewer UI 與 HTML lang 回退英文。

## 1. 責任、識別與觸發

使用者擁有工作方向、階段選擇與停止決定。Agent 可讀取事實、整理摘要、指出矛盾並建議下一步；只在使用者要求的範圍內操作 Task。討論、候選方案與建議，不等於採納或執行。

同一事情沿用同一識別，改名、改方向或轉階段不另開替代 Task。對象不明或有多張候選 Task 時，先讀取可得資訊並請使用者選定，不擅自覆寫或以新建規避辨識。新建時尚未取得識別，可在準備內容中標明待釐清；取得後更新 snapshot，不能把準備內容當成已成功建立。

以意圖辨識操作，不固定指令名稱或工具參數：

| 使用者意圖／例子 | 操作與界線 |
| --- | --- |
| 「把這個想法留存」 | 建立；先確認已有可理解目的，以及是否指向既有同一 Task。沒有方案或下一步仍可保存 Idea。 |
| 「讀這張 Task，告訴我現在做到哪」 | 讀取；回報目前紀錄與缺口，不順便寫入推測、同步外部進度或切換階段。 |
| 「更新剛才確認的方向與進度」 | 更新；只改已確定且在要求內的內容，沒有轉階意圖時不自動轉階。 |
| 「已開始實作，請記錄並切到實作」 | 更新＋切換階段；意圖、對象與事實都清楚時可一次處理，不重複要求同一授權。 |
| 「建議下一階段是什麼」 | 讀取＋建議；提出理由，仍不執行切換。 |
| 「確認結果達成，請完成結案」／「因需求取消，請結案」 | 結案；依實際意圖與結果／原因記錄完成、取消或停止。 |

「進展不錯」、「PR 合併了」、「換個方案如何」等訊息，本身不足以推出完成、轉階或採納。先指出具體缺口、提出必要問題；不要求使用者重新回答已清楚且仍有效的決定。更新由使用者按需要觸發，不背景監控、不承諾 Session 自動恢復或記得同步。

## 2. 共用操作契約

每次操作都先辨識對象、使用者要求與可得事實；讀取既有 Task 以保留未受影響內容及歷史。必要資訊不足時，停止受影響的寫入／轉階／結案，提出可供確認的摘要與必要問題。不能把尚待確認的候選內容保存成已定案；目的已知的 Idea 仍可保存其他未知欄位的明確待釐清標記。

| 操作 | 記錄效果 | 操作後回報 |
| --- | --- | --- |
| 建立 | 依既有共用結構保存名稱、目的、可得背景與實際階段；專案、標籤等未知項標待釐清。沒有方向時理由可不適用。 | 新識別與已保存摘要；未取得識別或未證實寫入時明示準備中／結果未知。 |
| 讀取現況 | 不修改 Task。目的、方向、階段、下一步／阻礙、重要變更與結案內容以 Task 本文為主。 | 紀錄現況、待釐清與參考存取限制；外部新事實另述，不能冒充 Task 已更新。 |
| 更新 | 修正要求內的目前 snapshot，保留其他內容；重要目的／方向調整另追加前後與理由。一般措辭修正不追加歷史。 | 哪些內容已改、哪些仍未知；不把本次沒有處理的欄位說成已確認。 |
| 切換階段 | 根據明確意圖與實際工作，更新目前階段和受影響摘要；重要跳轉／返回依內容規則追加歷史。 | 原階段、目前階段、理由及待釐清；不以文件／Skill／欄位填滿作為條件。 |
| 結案 | 階段為 Close，類型為完成／取消／停止，保存已知結果或實際原因；保留方向、參考、重要變更與未解問題。 | 結案類型、結果／原因，以及仍未解決的事項；之後可讀取回查。 |

回報須區分「整理好的候選內容」與「已證實保存」。若後續整合回報失敗或結果無法確認，明示實際情況；不能宣稱成功或自動另建替代 Task。具體重試、併發、原子性與工具錯誤格式留待整合設計，本契約不預定 wire shape。

## 3. 階段、切換與停止

主要路徑為 Idea → Draft plan → Implementation plan／實作 → PR → Close；它不是每張 Task 的必經程序。未結案階段可依實際工作跳轉或返回，也可在使用者決定不再繼續時直接結案。不要求逐一通過中間階段；Close 不自動返回，重開不在本輪。

| 階段 | 意義與典型觸發 | 使用者／Agent 責任與紀錄 |
| --- | --- | --- |
| Idea | 目的已知，要求留下發想。 | 使用者提供希望解決的問題；Agent 整理目的、可得背景與缺口。方向、理由、下一步或阻礙未知，不拒絕留存。 |
| Draft plan | 正在整理初步方案。 | 使用者決定是否採納；Agent 區分候選與已確認方向，保存可得理由及未決問題，不把討論寫成定案。 |
| Implementation plan／實作 | 準備或執行具體工作。 | 使用者／相鄰工作流程提供實際方向與進展；Agent 在既有背景或方向欄位整理進展，保存下一步及阻礙，不新增進展欄位或複製詳細步驟。 |
| PR | 工作進入交付或審查。 | 使用者／交付流程提供交付與審查情況；Agent 保存現況、後續行動與阻礙。PR 連結可選，沒有 GitHub PR 也可表達交付／審查。 |
| Close | 決定完成、取消或停止。 | 使用者決定類型並提供已知結果／原因；Agent 保存實際內容與未解問題，維持日後回查能力。 |

PR 建立或合併不推導結案；只要求更新 PR 合併情況時，Task 可以維持 PR。完成結案須有已知完成結果及結案意圖；取消記錄不再需要的原因，停止記錄決定不再繼續的原因。結案意圖、類型或結果／原因不明時，先釐清，不猜成「完成」。

Idea 可直接停止；實作發現新資訊可退回 Draft plan。切換時更新現在的 snapshot，不存每次切換的完整版本。重要歷史沿用 `<先後序號>｜<變更前> → <變更後>｜理由：…`，依發生順序追加，理由未知時明示待釐清，不補日期或理由。結案不是問題全解決：未解事項保留，下一步可為 `不適用：此 Task 已結案`。

## 4. 缺口、矛盾與參考

- 已知目的即可建立 Idea；目的本身不清楚，先問希望解決什麼，不從技術名詞猜目的。
- `待釐清：…` 表示未知，`無` 表示已確認沒有，`不適用：…` 表示此情境不適用；不混用、不留下占位文字或空白答案。
- 來源矛盾時保留差異及待確認點，不讓較新文字自動勝出。若只是提出另一方案，不取代已確認方向，也不追加虛構「已變更」歷史。
- 每筆參考沿用 `位置：…｜用途：…｜存取狀態：…`。無法讀取時保留位置與用途、說明缺少什麼；轉述不是 Agent 已讀原件。
- Task 本文保留目的、方向、階段與下一步或其缺口，不以「詳見文件」取代概要。詳細設計／測試由原流程維護，Task 不接管其產生、維護或同步。
- 新讀者無原對話仍可理解現況；未知下一步就如實未知，不補造待辦或已發生進展。

開發分支為 `docs/a129924/task-workflow-contract`。Archify 只協助理解本契約；PR Lens 只針對真實 base/head diff 產生本機變更圖；Graphify 沒有可用 graph 時採定點搜尋，不建立 graph／cache／hooks 或修改設定。這些文件與技能都不是 Task 使用或轉階的必要條件。
